# 抖音接入设计（待做）

> 2026-10-24 设计稿，尚未实现。发布和回复都人工，只做"抓数据 + 她挑评论 + 写草稿"。

## 一、分工

| 环节 | 谁做 |
| --- | --- |
| 选题 / 写脚本 / 生成视频 | 她（L1 全自动生产） |
| **发布** | **人工**（手机点一下） |
| **抓评论和数据** | 程序（浏览器自动化） |
| **挑评论 + 写回复草稿** | 她 |
| **发布回复** | **人工**（复制粘贴） |

## 二、技术路线

```
Playwright（Chromium，headful，独立 profile）
  → creator.douyin.com 登录一次（扫码）
  → 每 30 分钟打开「评论管理」页
  → 抓 DOM 文本（不调接口，避开 a_bogus 签名）
  → 存 state/douyin-comments.jsonl
```

**为什么不用接口**：抖音网页接口有签名（`a_bogus`），会变；DOM 结构变化慢得多。

**为什么 headful**：headless 特征更容易被识别。

## 三、数据流

```
① 抓取（定时 / 手动触发）
   state/douyin-comments.jsonl
   { id, videoTitle, user, text, time, replied }

② 她分析（唤起一次）
   「今天 12 条新评论，挑 3 条值得回的，写回复」
   → state/douyin-replies.json
   [{ commentId, user, text, reply }]

③ 面板「抖音」页
   ┌──────────────────────────────┐
   │ @小明：唱得真好        [复制回复] │
   │ 她写：「那当然，第一次有人这么说」 │
   └──────────────────────────────┘

④ 人工粘贴发布 → 面板点「已回」
```

## 四、抓什么

| 数据 | 来源 | 难度 |
| --- | --- | --- |
| 评论列表 | 创作者中心「评论管理」 | 中 |
| 播放/点赞/评论数 | 创作者中心「数据」 | 中 |
| 粉丝增长 | 同上 | 中 |
| 私信 | — | 高（验证码），**不做** |

## 五、风险与对策

| 风险 | 对策 |
| --- | --- |
| 登录态过期（几周~几月） | 面板提示"需要重新扫码" |
| 风控验证 | 频率 ≥30 分钟、headful、随机延迟 |
| 页面改版 | 选择器集中在一个文件，方便改 |
| 账号安全 | 专用浏览器 profile，不与其他混用 |

## 六、成本

| 项 | 估算 |
| --- | --- |
| 开发 | 2–3 天（抓取 1 天 / 她分析 1 天 / 面板 1 天） |
| 运行 | 每 30 分钟 10 秒，CPU 可忽略 |
| token | 每次分析 12 条 ≈ 5–10k，一天 20 次 ≈ 150k/天 |

## 七、里程碑

1. **M1**：能登录 + 抓到评论列表（存 jsonl）——先验证可行性
2. **M2**：面板显示评论，手动点「已回」
3. **M3**：接她分析，产出回复草稿
4. **M4**：抓数据（播放/点赞）画曲线

**先做 M1，跑通再往下。**

## 八、不做的事

| 不做 | 原因 |
| --- | --- |
| 自动发布 | 封号风险，不值得 |
| 自动回评论 | 同上 + 内容责任 |
| 私信抓取 | 验证码太频 |
| 点赞/关注操作 | 风控高危 |
